## Design summary

- Pure presentation controller `src/game/renderer/assembly.ts` (no THREE/DOM/
  clock/storage): five stages `base/frame/walls/roof/activation`, integer
  boundaries `floor(d*n/50)` (50-tick reference -> 0/6/16/28/38/50), per-part
  poses, `worldAssemblySnapshot(world, levelOf?)` adapter, upgrade module specs.
- `src/game/renderer/three/assemblyView.ts`: three.js view over the kit
  (`kitGeometry.ts`, generated from `docs/vision/assets/kit.json`, parity-tested);
  named pivot groups, one shared unit BoxGeometry + 10 palette materials;
  rebuild only on `asset|cell|rotation|level` signature change; idle mechanisms
  driven by `(tick, framePhase)`, identity under reduced motion.
- Timing authority stays in the economy: world reservations/sim charges decide
  WHEN; the renderer derives only WHAT to show from integer progress. Upgrade
  command IDs are idempotent (E02); reduced motion (U07) shows discrete static
  stages with identical economy fingerprints.

## Limitations

- **Capable visual inspection PENDING.** Non-vision agent: numerical phase,
  transform, occlusion and pixel-difference checks only; visual fidelity is a
  capable reviewer's verdict (architecture G1, #151).
- Renderer-side presentation only. The world<->sim level join in the harness is
  harness-side; production UI wiring is owed to #148 (cutover) / #199 (shell).
  `scene.ts` integration is #199's exclusive write path this round.
- Save/migration impact: none — no persistence schema or command changes;
  presentation derives from existing world/sim state.
- Small assets hold some stages (no new parts in that window); the warehouse
  shows all five distinct stages.
- Per-building named groups instead of full instancing for animated pivots
  (P1 scale tradeoff, #151 P02). Deck mounting assumes rest pose for animated
  groups; crane/turret/wall_gate are not upgradeable in P1.
