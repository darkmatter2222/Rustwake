# Offline catch-up: worker versus inline (B-02, spec 18.5, spec 21.5)

Measured 2026-11-03 on this machine with `node scripts/probe-catchup.mjs`.

## Method

* Runtime: one desktop Chrome instance driven by `playwright-core`, page viewport
  390 × 844 (the phone size the gallery uses), `npm run preview` on port 4173 serving the
  production build `index-Bvmh_oIQ.js` / `index-B8G4dl_D.css` / `catchup.worker-DphWaCEx.js`
  (that build differs from the shipped `index-ZDmIvNkZ.js` by one lease check inside the adoption
  flush, which runs on every adoption and cannot change a timed value by a measurable amount).
* Scenario: the mature yard `docs/evidence/yard-mature.json` (tick 18 298, 8 machines,
  18 links, four flying units, three research nodes) installed as the save with
  `payload.lastSeenMs` shifted back 12 h and the FNV-1a checksum recomputed, so the first
  thing the document does is credit one 12 h absence. The observed absence in the report is
  15 h 6 m because the seed's own reference time already lagged the capture by 3 h 6 m.
* Two runs, one per code path, each in its own browser context (spec 22.3: two tabs on one
  origin would share one `localStorage`):
  * **worker** — the shipped path: `catchUp` runs in `src/game/workers/catchup.worker.ts`.
  * **inline** — the same module with `Worker` removed by an init script before the bundle
    executes, so the identical function runs on the main thread.
* Instrumentation inside the page: `longtask` entries from a `PerformanceObserver` installed
  by the init script (so the very first task is counted), the two `performance.mark` entries
  the store writes around the handoff, the first paint entry, and one primary-tap repaint
  latency (tap, then two animation frames).
* The observer only reports tasks of **50 ms or more**, so "count 0" means no task reached
  50 ms rather than that the page did no work.

## Result

| Path | First paint | Long tasks | Median | p95 | Max | Over 100 ms | Handoff (mark → mark) | Input ack | Reconcile line after the gate |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| worker | 136 ms | 0 | – | – | – | 0 | 405 ms | 29 ms | 1 |
| inline | 36 ms | 1 | 281 ms | 281 ms | 281 ms | **1** | – (no handoff) | 31 ms | 0 |

Return report, identical in both runs: `Away 15h 6m · Your operation worked for 12h 0m
(capped) · Nonferrous +201 · Ferrous +38 · Wire +70 · Plates +228 · Deliveries 232 ·
Batches 747 · Bottleneck Storage full`.

## Reading

* The 12 h catch-up costs the main thread **281 ms** inline — over the 100 ms target of
  spec 21.5 — and **no long task at all** in the worker, which is the whole point of the
  handoff. The worker's 405 ms is wall-clock from posting the request to adopting the result
  (module fetch, compile, one round trip on a cold cache) and the page keeps painting during
  it; the store freezes its own ticks for exactly that window so nothing interleaves
  (spec 18.4).
* Input acknowledgement is unchanged by the choice (29 ms versus 31 ms against the 100 ms
  target), and the primary action really repaints: `Sell 39 Ferrous / +78 credits` becomes
  `Upgrade / 215 credits` after the ledger moves.
* First paint is *earlier* on the inline path (36 ms versus 136 ms) because that page never
  waits for the worker module; the worker page pays for a second network entry. Both are
  inside a normal load, and the reconcile line is what the player sees in the gap: the run
  counted one `.reconcile` node after the gate tap on the worker page and none on the inline
  page, where the work finishes before the HUD's first paint.
* The two paths agree exactly, which is the equivalence the fixtures promise: one shared
  function (`handleCatchUp`), one adoption path in the store, and six cases in
  `tests/simulation/catchup-worker.test.ts` pin the report, the clock advance, the refusal of
  a mismatched protocol version, and the "one absence per reference" rule.
* Below 20 000 ticks (2 000 s) of absence the store stays on the inline path, because one
  41.9 ms tick-by-tick pass over the full cap (the shipped `tests/perf/bench.test.ts` figure)
  means a short gap costs the main thread a few milliseconds and a worker hop would add a
  module fetch for nothing.

## Limits

One desktop Chrome instance, no thermal or device trace (**BL-01**), so these are page-level
numbers, not midrange-Android numbers; the phone multiplier is unknown but the two paths run
the same code, so the ordering is expected to hold. Long-task entries are quantised to at
least 50 ms, so the histogram cannot resolve sub-50 ms work. One run per path per process;
the spread across repeats was not recorded.
