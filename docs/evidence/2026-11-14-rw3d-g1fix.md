## Gap being fixed

Audit #129 (PR #189 product ruling) found G1: `src/app/store.ts` boot fell back to
`createInitialState()` on ANY `decodeSave` failure, silently discarding the corrupt
legacy payload. Executive contract: never silently reset a player's yard.

## Method / design

New module `src/game/persistence/recovery.ts` + integration in `src/app/store.ts`.
`GameStore` interface is UNCHANGED; `createStore` now returns
`GameStore & SaveRecoveryApi` (additive intersection), so every existing
consumer/test double (including forbidden-path files) is untouched.

- Recovery slot: `RECOVERY_KEY = "rustwake.save.recovery.v1"` holds the raw corrupt
  text VERBATIM (no wrapper — no quota inflation, byte-exact export).
- Write-once preservation (`preserveCorruptSave`): `preserved | already | occupied
  | empty | failed`. An occupied slot (a second, different corruption) is NEVER
  overwritten; both payloads survive sequential resolution.
- Boot: on any decode failure except `empty`, preserve the raw boot payload before
  the fresh yard is created. Notice + held state are re-derived STATELESSLY from
  storage content on every boot/reconcile (`refreshRecovery`), so they cannot drift;
  a signature comparison prevents spurious notifies on the 100 ms reconcile cadence.
- Held mode: if the preservation copy itself fails (quota), the corrupt bytes are
  held IN PLACE in `SAVE_KEY` and `persist()` is suppressed (`recoveryHeld`) so the
  fresh yard can never overwrite them. Recovery then goes export → repair → import
  → explicit discard.
- Transactional retry (`retrySaveRecovery`): decode the slot (slot-first target
  selection), migrate, write the recovered `SAVE_KEY` FIRST, and only then clear the
  slot. Any failure keeps the slot bytes. A guard refuses to overwrite a held,
  different `SAVE_KEY` corruption (`reason: "storage", detail: "save-key-corrupt"`).
- `exportSaveRecovery()` returns the exact raw text; `discardSaveRecovery()` is the
  only player-confirmed erase (writer-gated, reconcile-first).
- `clearSave` (reset) is UNCHANGED: it removes `SAVE_KEY` + `LEASE_KEY` only, so a
  reset never erases the recovery slot (verified headlessly, scenario C).
- Multi-tab: followers see the notice read-only; only the writer may retry/discard;
  reconcile preserves externally corrupted checkpoints write-once (safety write,
  not writer-gated).

### Decode-failure paths covered

`decodeSave` reasons: `parse`, `schema`, `checksum`, `invalid` are all preserved
(unit fixtures `bad-truncated`, `bad-schema`, `bad-checksum`, `bad-duplicate-id`,
`bad-negative-store`). `empty` is deliberately NOT preserved (nothing to retain —
a genuinely fresh start). Both entry points are covered: boot and reconcile
(external tamper). A failed manual import creates no slot. No payload size cap is
introduced: a 200,000-char corrupt payload is preserved verbatim (G2/#148 unchanged).

## Headless corrupt-boot exercise (real built app)

`docs/evidence/2026-11-14-rw3d-g1fix-corrupt-boot.mjs` boots the built app
(`vite preview`, headless Chrome) against poisoned localStorage. Results in
`docs/evidence/2026-11-14-rw3d-g1fix-corrupt-boot.json` (13/13 PASS, exit 0):

- A (checksum corruption): raw payload preserved verbatim at boot BEFORE the sim
  loop starts (A1/A2, sha256 match); fresh yard boots after the start gate and
  persists a checksum-valid save (A3); slot still verbatim after that persist (A4);
  repeated boot idempotent (A5/A6).
- B (truncated JSON / parse failure): verbatim preservation (B1), idempotent across
  reloads (B2), healthy yard persists (B3).
- C (save+lease removal — exactly the keys `clearSave` removes): recovery slot left
  intact (C1), fresh checksum-valid yard persists (C2).
- Z: zero page errors across all boots.

Probe notes: the app's start gate (`.gate__btn`) must be clicked before the tick
loop runs; boot-time preservation is asserted with the loop stopped. Seeding and
reload happen in one synchronous page task so a running loop cannot interleave.
In-page decodability mirrors `decodeSave`'s parse/schema/FNV-1a checksum stages.

## Limitations / owed UI wiring (coordinator: sequence before #151 G1)

1. **Owed UI wiring (blocking for G1):** no existing state-driven notice surface in
   `src/ui` can be fed without UI edits (verified read-only), and `src/ui` is a
   forbidden write path for this issue. The store therefore exposes the full state
   via `SaveRecoveryApi`: `getSaveRecovery()` (notice: slotKey, reason, detail,
   textLength, preserved), `retrySaveRecovery()`, `exportSaveRecovery()`,
   `discardSaveRecovery()`. A follow-up UI task must render a persistent,
   player-visible notice on corrupt boot with recovery/retry/export/discard actions
   BEFORE #151 can pass G1. Until then the fresh yard boots with the notice held in
   store state only — the preservation guarantee itself is complete and tested.
2. Visual inspection of any notice/recovery surface is PENDING (standing
   reservation; non-vision agent).
3. Retry/export/discard and quota-held paths are proven by unit tests (storage
   doubles), not by the browser probe — no UI buttons exist yet to drive them.
4. G2 (#148) oversized-payload rejection is untouched: no size cap added, existing
   rejection behavior preserved.
5. The probe's in-page decodability check covers parse/schema/checksum; full
   `validateSim` coverage lives in the unit suite.
