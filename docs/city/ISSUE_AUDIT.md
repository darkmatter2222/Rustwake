## Why most current issues deserve to exist
The earlier 50+ V2 items define durable domain/phase intent. Removing them would break feature traceability. Their weakness was granularity: giant tasks such as implement all 17 currencies, freight, hazards or regions are not good leaf assignments. Instead of erasing valuable acceptance context, we created small subtasks linked under specific workstreams, including an acyclic machine-readable DAG. Real productivity should be measured by merged/deployed tested functionality—not the number of closed checkboxes.

## Dispatch qualification rule
1. Workstream/phase/vision/master issues are **never developer-dispatchable**.
2. New leaf issue must appear in docs/city/execution-manifest.json and have all hard_blockers accepted at merged SHA, any external hold removed, a scoped write lease and a reproducible test plan. Written references to old broad capability issues (#267, #271, #283 etc.) are **scope pointers, not automatic circular hard blockers**; the manifest plus verified native GitHub dependency edges govern. Reconcile mismatches before work.
3. Reopened defects may be assigned as a new concrete issue with explicit acceptance; don't work on a closed V1 task.
4. Do not automatically re-open 192 items as ready. At most four child models run, with non-overlapping leased write paths; the coordinator works event-driven. GitHub Project 'Execution' field is an observation of current issue/PR/release evidence, not a substitute for it.
5. No new Project number is asserted until the host runs scripts/bootstrap-v2-city-project.mjs, verifies subissues/native blockers and reports the real URL and closed old board receipts.
