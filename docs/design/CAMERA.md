# Orthographic camera and pointer-grip design contract

## The observed failure
The original V2 camera calculated screen-delta pan using a simplified constant and yaw rotation without dividing the screen-up component by sin(camera elevation). At default 35.264° elevation, the terrain visibly slipped away from the cursor during click-hold drag. Wheel zoom also pivoted about center rather than terrain beneath the cursor. Fix implemented in src/camera.js and src/cameraInput.js, using exact screen-ground anchoring.

## Coordinate and projection math
World axes X east, Y up, Z south. Camera target on Y=0. Yaw 0 views from +Z, 45 approved default; elevation above horizontal. Orthographic frustum world height 80/zoom, CSS pixel canvas size W×H, pixel p relative to actual canvas rect. World units per CSS pixel k=80/(H*zoom). Horizontal screen-right component u=(px-W/2)k, vertical screen-up v=(H/2-py)k. Let theta=yaw, phi=elevation. Ground offset:
dx = cos(theta)u − sin(theta)v/sin(phi)
dz = −sin(theta)u − cos(theta)v/sin(phi).
This is the inverse of the world renderer's right/up camera basis. Test it, do not introduce approximations or separate HUD-specific math.

## Grab-to-drag invariant
At pointer-down record a single anchor world-ground position G under pointer p0. On each drag to p1, solve camera target so groundAtScreen(newView,p1)=G. This is exact even after many small moves; never accumulate guessed deltas. Applies to desktop left-drag and mobile one-finger pan. When the camera is intentionally clamped at target ±90 world units, the anchor can stop moving exactly at the boundary; document and visually communicate that limit.

## Zoom and orbit
Wheel/trackpad: capture ground under actual mouse location before zoom, compute bounded zoom, then adjust target to keep same ground under cursor. Handle DOM deltaMode pixels/lines/pages. Pinch: simultaneous zoom, twist yaw and centroid translation must maintain original world point under gesture centroid. On finger lift, reset remaining finger anchor; never turn the release into a build purchase.

Camera limits: zoom 0.20×–12×, yaw modulo 360°, elevation 20–80°, target ±90 world units; initial yaw45/elevation35.264, desktop zoom1.15, mobile zoom1. UI Zoom in/Zoom out buttons are explicit minimum-44px controls; wheel and pinch are not the only methods. Recenter/Home restores useful isometric view. Right drag or Shift drag rotates/tilts, Q/E orbit, arrow keys pan and Escape cancels a mode.

## Code boundaries
src/camera.js holds pure math, no browser or React dependencies. src/cameraInput.js owns the only mouse/pointer/wheel listeners on the world canvas and dispatches tap only after no movement/cancel. src/world.js renders using same orthographic frustum and updates camera matrix for immediate ray picking. src/App.jsx owns game commands and uses the controller's onTap; never let camera movement directly debit resources. World canvas reports read-only camera yaw/elevation/zoom/x/z and world3d stamps for browser evidence. Stamps do NOT authorize resource edits.

## CAM-03 zoom anchoring at all angles (#339)
CAM-01 made drag and in-envelope wheel zoom anchor-exact, but zoom that would push the pinned target past the ±90 pan envelope still hard-clamped the target (normalizeCamera) and slid the terrain — the 520.892780 px corner slip above. CAM-03 removes that slip for **every** zoom path (wheel, +/- buttons, pinch, programmatic fit) at **every** yaw/elevation across the **full 0.20–12 range**.

Design decision (anchor sacred, zoom clamps smoothly): no finite pan envelope is closed under arbitrary anchored zoom sequences, so extending the envelope cannot guarantee anchoring. Instead src/camera.js computes the raw pinned target per axis as `anchor + K/zoom` (monotone in zoom), so the feasible zooms form an interval containing the current zoom. `boundedZoom` binary-searches (64 iterations) from the feasible side to the nearest zoom whose anchored target still fits ±panExtent, then `pinGroundToPixel` pins exactly. The zoom therefore clamps **continuously** at the boundary instead of the target teleporting; the world point under the cursor/centroid never drifts and there is no jump. Center-anchored zoom (K=0, the +/- buttons and programmatic center fit) has zero target shift and always reaches both 0.20 and 12 exactly. A pure pan/twist that alone exceeds the envelope still clamps at the documented ±90 boundary (CAM-01 pan semantics unchanged); CAM-03 guarantees the **zoom** component is anchor-exact.

`zoomAtPixel` and `transformGesture` are the only changed functions; `groundAtScreen`, `pinGroundToPixel`, `panWithAnchor`, `orbitAtPixel`, `normalizeCamera` and all CAM-01 golden math are byte-identical. src/world.js `applyCamera`/`stampCamera` are untouched: the canvas dataset is still stamped synchronously from the rendered THREE camera, so dataset == applied state at all angles (#307 method hashes preserved).

## CAM-08 pointer ownership and gesture rebase (#344)
CAM-01/CAM-03 made the anchor math exact; CAM-08 makes the POINTER BOOKKEEPING that feeds it survive the ways a real browser ends a contact early: `lostpointercapture`, `pointerout`, out-of-window release, `buttons===0` hover on a stale track, and touch cancellation. All recovery is canvas-owned — no window/document listeners, timers, storage or sim transactions.

Design decisions (src/cameraInput.js):
- Per-pointer tracks (Map) with per-pointer `moved`/`gestured` flags replace the shared `dragged` boolean, so a real two-finger transform marks BOTH participants and neither lifts into a tap/purchase; a stationary second finger keeps its own tap semantics.
- `purgePointer` rebases every survivor's anchor from the CURRENT ground under its continuing pixel before deleting the dropped track — a finger lift or cancel therefore causes zero target jump and the survivor keeps panning on its existing track (no fresh press).
- `setPointerCapture` is guarded (inactive-pointerId `NotFoundError` swallowed, bookkeeping still completes); `releasePointerCapture` on up/cancel/purge/dispose is guarded and idempotent.
- `lostpointercapture` purges the dropped pointer; `pointerout` purges ONLY when capture is not held (a captured drag legitimately leaves the canvas); `onMove` purges any tracked pointer reporting `buttons===0` BEFORE pan/pinch, so hover can never ghost-drag from a dead anchor.
- `pointercancel` marks the track gestured (no purchase) and purges; a late `pointerup` for the cancelled id is inert. `dispose()` removes all 8 listeners and releases held captures.

The anchor math (`groundAtScreen`/`panWithAnchor`/`transformGesture`/`zoomAtPixel`) and src/camera.js are untouched; src/world.js `applyCamera`/`stampCamera` are byte-identical (#307 hashes f3afa5479a66b97e len 602 / 691b3c0a3480e97b len 252, hash-verified at the capture head). Yaw 45 / elevation 35.264 and synchronous dataset stamps preserved.

## CAM-05 panel transitions retain camera intent and selection (#341)

The observed failure: opening or closing any toolbar panel (build catalog, roads, fleet, research, market, or the inspector via the select tool), the sheet collapse toggle, the freight-ledger chip (the separate seventh `inventory` panel), or a responsive viewport resize could refit the camera to an empty plot and/or silently drop the selected machine. Root causes in src/App.jsx: `choose()` cleared `selectedId`, the mode-change effect called `updatePlacement(true)` (auto-frame), and the ResizeObserver also called `updatePlacement(true)`. CAM-01/CAM-03 made gestures anchor-exact; CAM-05 makes **UI transitions** intent-preserving. Only an explicit Home/Recenter (or a reset command) may refit.

Policy — one pure decision point, `transitionCamera({trigger,…})` in src/inspector.js (no React/browser dependency):
- `trigger:"panel"` and `trigger:"resize"` return the camera **by reference** (identity, not a copy). A panel open/close, sheet collapse/expand, ledger open/close or viewport resize can never move the camera, even if the selected machine is obscured by the new panel geometry.
- `trigger:"selection"` and `trigger:"settings"` reframe via `frameSelection` **only** when `obscured && autoFrame && building` — the UX-04 (#362) non-obscuring auto-frame for a genuinely new selection or an explicit settings change. An unobscured machine, or the player's auto-frame opt-out, keeps the pose.
- `trigger:"focus"` (the explicit Focus button) always reframes to the panel-aware focus pixel.
- `trigger:"reset"` is the **only** refit: `normalizeCamera(home)` with home yaw 45 / elevation 35.264 / zoom 1.15 desktop (≥960px) or 1 phone / target (0,0). Out-of-range home inputs clamp through the same normalizeCamera as every other path.

Selection retention — `nextToolMode(toolId,selectedId)` in src/dock.js: the Inspect tool re-enters `inspect` mode when a selection is retained, otherwise `select`; every other tool keeps its own mode. `choose()` never clears `selectedId`; closing the sheet returns to `select` mode with the selection retained in state (the panel-host unmounts, the selection does not). Explicit deselect remains: empty-ground tap, Escape, dismantle. Escape deselects without touching the camera pose.

## CAM-02 interaction state machine: click vs camera gesture (#338)

The observed failure: the pre-CAM-02 controller used one uniform `>6px` movement heuristic and a release-pixel pick, so a 5px mouse drag or a middle/shift press could commit a build, an orbit+click button chord re-armed a fresh track and purchased on the non-final release, a wheel zoom during a held press still tapped on release, and sub-threshold jitter across a cell boundary committed the WRONG cell. CAM-02 replaces the heuristic with ONE explicit interaction state machine in src/cameraInput.js: a contact sequence is either a **click** — the only thing that may commit a build/road or change selection — or a **camera gesture** that must NEVER spend materials.

States and transitions (per-pointer track in the existing CAM-08 Map; session mode `idle` → `single` → `multi`):
- `press` — pointerdown creates the track: down pixel, button, anchor, type slop, `primary = (button===0 && !shiftKey)`, and `downCell` picked from the CURRENT rendered view (world.setView + applyCamera before screenToCell; a ray that misses the ground yields the out-of-bounds sentinel {x:−1,z:−1} that gameplay dispatch rejects, never a crash).
- `press → pan` — displacement from the down pixel reaches the type click-slop: **mouse/pen 5 CSS px, touch 10 CSS px** (`CLICK_SLOP`). The latch is permanent: once `moved` is set, returning to the down pixel never re-arms a click. Pan uses the CAM-01 anchor-exact `panWithAnchor`.
- `press → orbit` — right button, shift-held, or shift-at-down (`orbitIntent`) movement past slop rotates/tilts; a stationary right or shift press is still never a click.
- `press → multi` — a second contact starts the two-finger transform; a real pinch/twist/centroid-pan marks BOTH participants `gestured` with phase `multi`, so neither finger lifts into a tap (a stationary second finger that never transforms keeps its own tap semantics, per CAM-08).
- `press → chord` — a mouse reports every button change as pointerdown on the SAME pointerId. A secondary press during an existing contact keeps the original down pixel/button/anchor and marks the track `gestured` (phase `chord`) instead of resetting it; a non-final button release (`e.buttons!==0`) keeps the contact alive and gesture-marked. Only the FINAL release may classify, and a chorded contact never taps.
- `press → gesture` — ANY camera command issued while a pointer is in contact (wheel, Q/E rotate, arrow-key pan, zoom buttons — all routed through `markContactGesture`) revokes commit eligibility of every tracked pointer.
- `purged` — pointercancel, lostpointercapture, uncaptured pointerout or `buttons===0` hover delete the track via the CAM-08 `purgePointer` (survivor anchors rebased from current ground, zero target jump); a late pointerup for a purged/cancelled id is inert.

Tap emission rule — `onTap` fires only when ALL hold at the final release: (1) the track still exists; (2) the session was single-pointer (`!wasMulti`); (3) `!moved` (displacement stayed STRICTLY below the type slop); (4) `!gestured` (no transform, chord or camera command during contact); (5) `track.primary && e.button===0` (right/middle/back/forward and shift-orbit intent never commit); (6) the commit cell is `track.downCell` — the cell picked at POINTER DOWN, never the release pixel, so jitter across a cell edge or camera motion during the press cannot redirect a commit. The controller exposes a read-only `state()` snapshot ({mode, pointers:[{id,phase,moved,gestured,button,primary}]}) for tests and evidence; it mutates nothing.

Mouse vs multi-touch parity: the same classifier serves mouse, pen and touch — only the slop differs (5/5/10 CSS px, touch wider for finger jitter). Right-drag/shift orbit on desktop corresponds to two-finger twist on phone; wheel zoom corresponds to pinch; both paths mark gestured contacts and neither spends. Road building is two clean clicks (origin arms without spend, destination paves the route exactly once); any drag in road mode pans the camera and paves nothing. Select-mode taps select without spending. Spend authority stays where it was: src/App.jsx owns game commands via `onTap`; the camera controller never debits resources itself, and src/camera.js anchor math plus src/world.js `applyCamera`/`stampCamera` are untouched (#307 hashes preserved).

Composition: CAM-08 (#344) owns pointer BOOKKEEPING (capture hygiene, purge/rebase, cancel survival) — CAM-02 builds the click/gesture CLASSIFIER on top of those same per-pointer tracks and adds the slop latch, chord handling, camera-command marking and down-cell commit.
